# Audit de FarfaLauncher (23/11/2026, v1.2.1)

Audit en lecture seule, phase 1 du chantier « stabilité, documentation, autonomie ».
Le NAS, RomM, FarfaRomManager et `outils/surveille-rapports` sont dans
`FarfaRomManager/docs/audit-2026-11.md`.

État au moment de l'audit : `tsc` sans erreur, `cargo test --lib` = 203 réussis,
24 ignorés (e2e qui demandent un vrai serveur). Pas de test de l'interface.

## 1. Comment le launcher fonctionne

| Étape | Code | Ce qui se passe |
|---|---|---|
| Connexion | `commands/session.rs` | Heartbeat RomM, puis code appareil, code d'appairage ou token collé. Token rangé dans le trousseau du système (`secrets.rs`). |
| Bibliothèque | `commands/library.rs:80` `start_refresh` | `assets.json`, catalogue du gestionnaire (`manager.rs`), puis plateformes et ROM RomM. |
| Téléchargement | `install/download.rs` | Depuis RomM (`api/roms/{id}/files/content/…`) ou le gestionnaire (`files/{sha1}`), reprise et contrôle SHA-1/MD5. |
| Installation | `install/` (recomp, émulateur), `pc/` (jeux « Ordinateur », Proton sous Linux) | Extraction, `preparer:`, registre `installed.json`. |
| Lancement | `commands/launch.rs:66` → `play.rs` → `launch/` | Sauvegarde, langue, manettes, liens, shaders, puis suivi du processus. |
| Après la partie | `save_sync.rs`, `stats.rs` | Envoi de la sauvegarde et du temps de jeu ; file locale si hors ligne. |

Le token RomM sert aussi d'identifiant auprès du gestionnaire (`manager.<domaine>`) et
du serveur d'assets (`assets.<domaine>`).

**Mises à jour** (`commands/update.rs`) : canal stable (`releases/latest`), bêta
(`canal-beta`), test d'un rapport (`test-<rapport>-<n>`). Signées avec minisign, clé publique
dans `tauri.conf.json`. Vérifiées au démarrage puis toutes les 30 min.

**Hors ligne** : seul le heartbeat RomM est surveillé (`offline.ts`). Les jeux installés
restent jouables, sauvegardes et temps de jeu passent en file. Installer une recomp ou un
émulateur échoue si le gestionnaire est injoignable.

### Corrections de la phase 1 (branche `phase1-fix`, 2026-11-23)

Un commit par bug (« Correctif Lx : … »). Détails utiles pour relire :

- **L2, L3** : nouveau module `safe_file.rs`. Un fichier illisible est renommé en
  `<nom>.illisible-<AAAAMMJJ-HHMMSS>` (journalisé) au lieu d'être écrasé ; écritures par un
  fichier temporaire au nom unique. Le registre est modifié sous un verrou (`REGISTRY_LOCK`).
  Au démarrage, `settings.json` n'est écrit que s'il n'existe pas, et les `*.tmp` abandonnés
  de plus d'une heure sont effacés (`1fb334c`).
- **L4** : un 401 n'efface le token que s'il est en JSON (`{"detail": …}`, réponse de RomM).
  Un 403 au démarrage renvoie à l'écran de connexion avec une explication, token gardé ; dans
  l'interface, seul `auth_invalid` déconnecte (`865ff3c`).
- **L6** : `send_stream` (60 s pour les en-têtes) et `read_body` (60 s sans données) dans
  `romm/client.rs`. Pas de `read_timeout` global de reqwest : il compterait aussi le temps
  d'envoi des gros fichiers (sauvegardes, rapports) et les couperait.
- **L7** : `error::LockOrRecover` (`m.lock_or_recover()`), remplacement mécanique de tous les
  `.lock().unwrap()` du code (même sens, sans panique). Une valeur reprise après une panique
  peut être un peu fausse (un jeu resté « occupé ») : c'est préférable à un launcher bloqué.
- **L9** : une seule fonction `launch::kill_tree` (groupe de processus sous Linux/Mac,
  `taskkill /T /F` sous Windows).
- **L10** : Linux seulement, si le Secret Service manque : token dans `<config>/token.json`
  (droits 0600), comme `farfalauncherdeck`. Windows et Mac : trousseau seul, comme avant.
- **L13** : `AppState::start_running` et `mark_busy` prennent les mêmes verrous dans le
  même ordre (installs → running → busy).
- **L16** (fait car simple) : `with_base` ne transmet le token qu'à la même machine ou au
  même domaine enregistrable que RomM (une IP : seulement la même adresse). Un 401 du
  gestionnaire ou des assets ne déconnecte jamais de RomM (`a0baf70`).
- **L5** : seule une lettre de lecteur en tête d'un morceau (`C:`) est retirée ; les autres `:`
  restent (`d2cd211`).
- **L1** : sous Linux, `group_alive` lit `/proc` (le `kill -0 -<groupe>` sans `--` réussissait
  toujours avec le `kill` d'Ubuntu) ; Mac : `kill -0 -- -<groupe>` (`5b1931e`).

**L8, limite connue (non corrigée)** : sous Linux, la partie dure tant qu'un processus du
groupe du jeu existe. Un jeu (ou un lanceur) qui crée sa propre session (`setsid`, double
`fork`) en sort : le launcher croit la partie finie (temps de jeu, sauvegardes envoyées trop
tôt). La correction sûre demanderait `PR_SET_CHILD_SUBREAPER` sur tout le launcher (les
processus orphelins deviennent ses enfants et il doit les ramasser lui-même) : trop risqué
pour une correction minimale.
À revoir si un jeu précis est signalé.

**Reste pour la phase 2** : L14, L15, L17, L18 (sauf les deux `kill`, fusionnés par L9),
L19.

## 6. Parité Windows / Linux

Ce qui n'existe ou ne marche bien que sous Windows : réponses automatiques aux fenêtres
(`dialogs.rs`), menu en jeu au premier plan (`ingame.rs`), détection de fenêtre pour les
plantages, e2e d'émulateurs (`#[cfg(windows)]`). Le Deck stocke son token en clair
(`~/.config/farfalauncherdeck/token`, 0600). `test.yml` ne compile pas pour Mac.
